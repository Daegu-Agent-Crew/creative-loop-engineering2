# DECISIONS — CLE3 수렴 루프 시스템 도입

## D-001: GOAL/STATUS 진행률 수치 재기준화
**결정일**: 2026-08-14
**배경**: GOAL.md에 "EP001 17/49, EP002 30/57"로 기재되었으나, 실제 리포 조회 결과 EP001 16개, EP002 0개(`episodes/` 기준). 10개의 EP002 이미지가 `cle5-ep002/images/`에 비정규 경로로 존재.
**결정**: 진행률을 3단계로 분리하여 표기 — `generated`(원본 생성) / `qa_approved`(QA 통과) / `published_final`(오버레이+공개본). GOAL.md의 기준선 수치 수정.
**근거**: "49/49 생성"만으로는 수렴 루프의 효과를 검증할 수 없음 (sfex11 코멘트 §1).

## D-002: 신규 작성 대상 명확화
**결정일**: 2026-08-14
**배경**: GOAL/PLAN이 `run-panel-jobs.js`, `evaluation-rubric.md`, `IMAGE-WORKFLOW.md`, `AI-COLLABORATION-PROTOCOL.md`를 "개편/개정" 대상으로 지정했으나, 이 파일들이 three-body-comic repo에 존재하지 않음.
**결정**: 이 파일들은 "개편"이 아닌 **신규 작성**으로 분류. PLAN.md의 "전면 개편" 표현을 "신규 작성"으로 수정.
**영향**: 작업량 추정이 달라짐. 기존 코드를 수정하는 것보다 처음 설계하는 것이 더 많은 설계 결정을 요구함.

## D-003: 구현 순서 — Evaluator를 루프보다 먼저
**결정일**: 2026-08-14
**배경**: 원안 PLAN은 Phase 2(마이크로 루프)를 Phase 3(Evaluator)보다 먼저 실행. 그러나 평가 기준 없이 루프를 돌면 수렴을 보장할 수 없음.
**결정**: 구현 순서를 다음과 같이 조정:
1. 비교·선택 데이터 스키마 설계
2. A/B/C Evaluator + 절대 품질 게이트 (both_bad/tie 포함)
3. 후보 생성 실행기 (Panel Runner)
4. 선호 메모리 & 레퍼런스 체인
5. 에피소드 회고 & 캘리브레이션
**근거**: sfex11 코멘트 §3 "구현 순서 수정".

## D-004: 절대 품질 게이트 유지
**결정일**: 2026-08-14
**배경**: A/B 비교평가만 사용하면 후보가 모두 불량일 때 "덜 나쁜 것"이 선택되어 preference memory를 오염시킬 수 있음.
**결정**: A/B 비교와 병행하여 절대 품질 게이트(最低 기준)를 유지. `both_bad` → 전부 재생성, `tie` → 둘 다 유지하고 회귀 데이터로 활용.
**근거**: sfex11 코멘트 §3 "A/B 평가는 탐색용으로 사용하되 기존 절대 품질 게이트를 완전히 제거하면 안 됨".

## D-005: Phase 4 / Phase 5 평가 범위 분리
**결정일**: 2026-08-14
**배경**: 현재 루브릭은 Phase 4에서 한글 렌더링을 평가하나, 생성 정책은 `final_text_in_image: false`(대사 후처리). 모순.

**근거**: sfex11 코멘트 §6 "평가 규칙 정리".

## D-006: 후보 파일 관리 — Git 미커밋, 임시 영역
**결정일**: 2026-08-14
**배경**: 패널당 2~3후보 × 2~3회 반복 = 잔여 패널 기준 128~288회 생성. 모두 Git에 커밋하면 리포 비대.
**결정**: candidate/rejected 파일은 임시 작업 영역(`tmp/` 또는 `.candidates/`)에 보관. 선택된 최종본만 `episodes/*/panels/`로 승격. 체크포인트는 승인 패널 5~10개 단위.
**근거**: sfex11 코멘트 §5 "저장·비용 기준".

## D-007: 검증 전략 — 단일 패널 end-to-end 먼저
**결정일**: 2026-08-14
**배경**: 처음부터 32패널에 전수 적용하면 비용만 소모하고 효과 검증이 어려움.
