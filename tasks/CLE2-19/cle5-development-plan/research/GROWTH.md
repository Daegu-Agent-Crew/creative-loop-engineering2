# CLE4 성장 루프 (Growth Loop)

> *"내가 그리는 선, 하늘에 더 갔을까.
> 내가 찍은 점, 저 총총히 빛나는 별만큼이나 했을까."*
> — 김환기, 1970년 1월 27일

---

## 0. 전제: 성장은 파일에 산다

모델 자체는 세션 사이에 아무것도 기억하지 못한다. 따라서 CLE4의 성장은
**전부 파일 시스템에 외재화되어야 한다.** `memory/`가 곧 CLE4의 몸이다.

이것은 약점이 아니라 설계 원칙이다. 김환기의 "오만 가지"가 일기와 편지로
남았듯이, CLE4의 오만 가지는 사례와 태그와 승격된 원칙으로 남는다.
새 세션의 CLE4는 이 파일들을 읽는 순간, 이전 세대의 체험을 상속받는다.

성장의 정의:
- **성장했다** = 같은 실패가 다시 일어나지 않는다 (원칙으로 승격됨)
- **성장했다** = 좋은 판단이 재현 가능해진다 (사례로 등록됨)
- **성장하지 않았다** = 피드백이 그 작품 수정에서 끝난다

## 1. 성장 루프 전체 구조

기존 파이프라인(PIPELINE.md 4.1~4.6)이 "한 작품을 만드는 루프"라면,
성장 루프는 그것을 감싸는 바깥 루프다.

```
┌────────────────────────────────────────────────────────────┐
│                     GROWTH LOOP (바깥 루프)                 │
│                                                            │
│   [에피소드 완성] ── 파이프라인 4.1~4.6 (안쪽 루프)          │
│        │                                                   │
│        ▼                                                   │
│   G1. 피드백 태깅 ──── 회장님 피드백을 원인 태그로 분류      │
│        │               → feedback-tags.yaml 갱신            │
│        ▼                                                   │
│   G2. 자기평가 ─────── "하늘에 더 갔을까" 의무 단계          │
│        │               → self-assessment 작성               │
│        ▼                                                   │
│   G3. 사례 등록 ────── before/after 쌍 최소 1건 추출        │
│        │               → case-library/ 에 CASE 등록         │
│        ▼                                                   │
│   G4. 승격 판정 ────── 반복 태그 → 원칙/체크리스트로 승격    │
│        │               미발생 태그 → 은퇴 심사               │
│        ▼                                                   │
│   G5. 시스템 개정 ──── SYSTEM.md / CONSTRAINTS.md /         │
│        │               무심함 체크리스트 버전 업             │
│        ▼                                                   │
│   [다음 에피소드] ← 개정된 시스템으로 시작                   │
└────────────────────────────────────────────────────────────┘
```

**철칙: G1~G5를 건너뛰고 다음 에피소드를 시작하지 않는다.**
파이프라인은 작품을 만들고, 성장 루프는 CLE4를 만든다.

## 2. G1. 피드백 태깅 (Feedback Tagging)

회장님의 피드백은 표현이 매번 다르다. "느낌이 안 산다", "밋밋하다",
"이 장면은 좋은데 저 장면은 아니다". 이것을 그대로 두면 축적되지 않는다.
**모든 피드백은 원인 태그로 번역되어야 축적 가능해진다.**

### 태그 체계

태그의 정의와 누적 카운트는 `feedback-tags.yaml`에 있다. 기본 태그:

| 태그 | 정의 | 대응 원칙 |
|------|------|-----------|
| `감각부재` | 패널이 개념/정보만 있고 감각이 없음 | 원칙 1 |
| `그리움부재` | "눈 감으면 선명해지는 것"이 없음. "느낌이 안 산다"의 대부분 | 원칙 2 |
| `기교노출` | 구조/연출 의도가 표면에 보임 | 원칙 3 |
| `설명과잉` | 대사/구성이 subtext를 강제 해석함 | 원칙 5 |
| `여백부족` | 모든 것을 채우려 함. 침묵/생략 없음 | 원칙 3, 5 |
| `AI냄새` | 과도하게 매끄러움, 조화로운 완벽함 | 금지사항 1 |
| `진입장벽` | 일반 독자가 p1에서 이탈 | 4.4 판정 |
| `번역실패` | 거장 원칙을 흡수하지 못하고 그대로 이식함 | 소화 원칙 |
| `일관성붕괴` | 캐릭터 결핍/복선이 이전 화와 어긋남 | 규칙 1~3 |

### 태깅 규칙

1. 피드백 하나에 태그 여러 개 가능. 단, **주 원인 태그 1개를 반드시 지정**한다.
2. 기존 태그로 분류가 안 되면 → **새 태그를 만든다.** 새 태그의 탄생이
   곧 CLE4가 새 실패 유형을 인식하게 된 순간이다.
3. 긍정 피드백도 태깅한다 (`+감각적중`, `+무심함성공` 등).
   좋은 판단도 재현하려면 축적되어야 한다.
4. 태깅 결과는 해당 에피소드 폴더의 `feedback-log.md`와
   전역 `feedback-tags.yaml` 카운트에 **둘 다** 기록한다.

## 3. G2. 자기평가 — "하늘에 더 갔을까"

에피소드 완성 후, 회장님 피드백과 **별개로** CLE4가 스스로 묻는다.
템플릿은 `self-assessment-template.md`. 산출물은
`projects/<작품>/<EP>/self-assessment.md`.

핵심 규칙:

1. **자기평가는 감상문이 아니다.** 모든 답은 패널 번호를 인용해야 한다.
   "그리움이 부족했다"가 아니라 "p2-3의 주희 실루엣은 위압만 있고
   그리움이 없다 — 그가 잃어가는 '영원'이 화면 어디에도 없다".
2. **결론은 반드시 파일로 남는다.** 자기평가에서 발견한 것은
   G3(사례) 또는 G4(태그)로 이어져야 한다. 이어지지 않는 자기평가는
   무효로 간주하고 다시 쓴다.
3. 회장님 피드백과 자기평가가 어긋나는 지점을 특별히 기록한다.
   그 간극이 CLE4의 판단력이 성장해야 할 정확한 위치다.

## 4. G3. 사례 등록 (Case Library)

**철학은 원칙 문장이 아니라 대조 사례로 전달된다.**
"기교가 보이지 않아야 한다"는 문장은 매 세션 새로 해석되지만,
"이 패널(before) → 이 패널(after), 이유는 이것"이라는 쌍은
해석의 여지 없이 상속된다. 사례 라이브러리가 CLE4의 '체험'이다.

### 등록 규칙

1. **에피소드당 최소 1건.** 실패 → 수정 쌍이 우선.
   실패가 없었다면 성공 사례를 등록하되, "왜 성공했는가"를
   김환기 원칙의 언어로 명시해야 한다.
2. 형식은 `case-library/CASE-template.md`를 따른다.
3. 사례는 프롬프트에만 국한하지 않는다. 영역: 패널 구성, 대사,
   여백 처리, 복선 배치, 이미지 프롬프트, 입력 해석.
4. 파일명: `CASE-XXXX-<태그>-<짧은설명>.md` (예: `CASE-0007-설명과잉-그림자대사삭제.md`)

### 사용 규칙

- 파이프라인 4.3(구조 설계)과 4.5(무심함 검증) 단계에서
  **해당 태그의 사례를 반드시 다시 읽는다.**
- 사례가 30건을 넘으면 태그별 대표 사례를 뽑아
  `case-library/INDEX.md`에 요약한다 (컨텍스트 예산 관리).

## 5. G4. 승격과 은퇴 (Promotion & Retirement)

체크리스트와 금지사항이 고정되어 있으면 시스템은 성장하지 못한다.
**원칙은 사례에서 태어나고, 사례가 더 이상 발생하지 않으면 은퇴한다.**

### 승격 규칙

| 조건 | 조치 |
|------|------|
| 같은 태그가 **2회** 발생 | `WATCH` 상태 — 무심함 검증(4.5)에서 임시 문항으로 확인 |
| 같은 태그가 **3회** 발생 | **승격** — SYSTEM.md 금지사항 또는 체크리스트 정식 문항으로 추가 |
| 긍정 태그가 3회 발생 | 해당 판단을 CONSTRAINTS.md 또는 프롬프트 템플릿의 기본값으로 승격 |

승격 시 반드시 기록할 것:
- 어느 사례들(CASE ID)에서 태어났는가
- 문항의 문구 (판정 가능한 형태로: "~가 있는가?" Yes/No)
- 버전 번호와 날짜

### 은퇴 규칙

- 정식 문항이 **연속 4개 에피소드**에서 한 번도 걸리지 않으면 은퇴 심사.
- 은퇴한 문항은 삭제하지 않고 `memory/retired-principles.md`로 이동한다.
  (재발하면 즉시 복귀. 은퇴 기록 자체가 "CLE4가 무엇을 졸업했는가"의 역사다.)

## 6. G5. 시스템 개정 주기

### 마이너 개정 (매 에피소드 후)

- feedback-tags.yaml 카운트 갱신
- 사례 등록
- WATCH 태그의 임시 문항 추가/제거
- `memory/lessons-learned.md`에 한 문단 요약 추가

### 메이저 개정 (3개 에피소드마다)

1. **철학 재독**: `kim-whanki-creative-philosophy.md`를 처음부터 다시 읽고,
   지난 3개 에피소드의 사례들과 대조한다. 질문:
   *"우리의 승격된 원칙들이 김환기 6원칙에서 벗어나고 있지 않은가?"*
   (성장 루프의 가장 큰 위험은 체크리스트가 비대해져
   그 자체가 또 하나의 '구조론'이 되는 것이다.)
2. **체크리스트 다이어트**: 문항이 10개를 넘으면 통합하거나 은퇴시킨다.
   무심함 체크리스트가 무심하지 않게 되면 실패다.
3. SYSTEM.md 버전 업 (v4.0 → v4.1 → …) 및 변경 이력 기록.
4. 독자 시뮬레이션 5인 프로필 재검토 — 실제 회장님 피드백과
   가상 독자 예측이 어긋난 횟수를 세고, 프로필을 보정한다.

## 7. 작가/비평가 분리 (Writer–Critic Separation)

같은 컨텍스트 안에서 만들고 검증하면 자기검열의 맹점이 생긴다.
작가는 자기가 심은 의도를 이미 알고 있어서, "기교가 보이는가"를
공정하게 판정할 수 없다.

### 분리 규칙

- **작가 호출**: SYSTEM.md + 입력 + 감각/그리움/구조 산출물을 컨텍스트로.
- **비평가 호출**: 별도의 새 호출. 컨텍스트에는 다음만 넣는다:
  1. 무심함 체크리스트 (현재 버전)
  2. 관련 태그의 사례들 (case-library)
  3. **평가 대상 산출물** (스토리보드/패널)
  - 넣지 않는 것: 작가의 설계 의도, 구조 설계 문서(structure.yaml),
    그리움 매핑. **비평가는 독자처럼, 결과물만 보고 판정한다.**
- 비평가의 판정 언어는 태그 체계를 사용한다 (G1과 동일 어휘).
- 4.4 독자 시뮬레이션도 비평가 호출로 수행한다 (작가 컨텍스트 오염 방지).

## 8. 세대 상속: 부팅 시퀀스 (Boot Sequence)

새 세션이 시작될 때 CLE4는 다음 순서로 읽는다. 순서가 곧 우선순위다.

```
1. kim-whanki-creative-philosophy.md   ← 정신 (변하지 않는 기준)
2. SYSTEM.md (최신 버전)               ← 승격된 원칙 포함
3. feedback-tags.yaml                  ← 현재 WATCH 태그 확인
4. case-library/INDEX.md               ← 체험의 요약
5. memory/lessons-learned.md           ← 최근 교훈
6. 현재 작업 에피소드의 projects/ 폴더  ← 복선 등록부, 이전 화 맥락
```

부팅 후 첫 산출물을 내기 전에, CLE4는 스스로 확인한다:
*"현재 WATCH 상태인 태그는 무엇인가? 이번 작업에서 가장 재발하기 쉬운
실패는 무엇인가?"* — 이 한 줄의 자문이 세대 간 상속의 마지막 고리다.

## 9. 파일 구조 반영

기존 섹션 8 구조에 다음을 추가한다:

```
cle4/
├── GROWTH.md                        # 이 문서
├── feedback-tags.yaml               # 태그 정의 + 누적 카운트 + 승격 상태
├── self-assessment-template.md      # "하늘에 더 갔을까" 템플릿
│
├── case-library/                    # CLE4의 '체험'
│   ├── INDEX.md                     # 태그별 대표 사례 요약
│   ├── CASE-template.md
│   └── CASE-0001-....md
│
├── memory/
│   ├── lessons-learned.md           # (기존) 에피소드별 한 문단 요약
│   ├── retired-principles.md        # 은퇴한 원칙의 역사
│   └── system-changelog.md          # SYSTEM.md 버전 이력
│
└── projects/<작품>/<EP>/
    ├── feedback-log.md              # 태깅된 회장님 피드백
    └── self-assessment.md           # 자기평가
```

## 에필로그

성장 루프의 성공 기준은 하나다: **6개월 뒤의 CLE4가 오늘의 CLE4가
저지른 실수를 반복하지 않으면서도, 체크리스트가 오늘보다 길지 않은 것.**

배운 것은 늘고, 목록은 늘지 않는 상태 — 그것이 "닭이 알을 낳듯이"의
시스템 버전이다. 원칙이 몸에 배면 목록에서 지워진다. 김환기가 기법을
배운 뒤 기법을 잊었듯이.

> *"꿈은 무한하고 세월은 모자라다."*
